# עדכון האתר: שינוי → תצוגה מקדימה → אישור → אתר חי

המשתמש רוצה לבקש שינוי במילים פשוטות, לראות איך הוא נראה, ולהחליט אם הוא עולה לאוויר. האתר הוא אתר עסקי של לקוח, ולכן שום דבר לא מגיע לאתר החי בלי שהמשתמש ראה ואישר.

`CLAUDE.md` שבשורש הפרויקט הוא מקור האמת למצב הפרויקט. הוא נטען אוטומטית, ואת מה שכתוב שם לא חוזרים לבדוק. הסקיל הזה מוסיף את תהליך העבודה ואת המפה של איפה כל דבר נמצא.

## 0. לפני שנוגעים בקוד

```bash
git fetch -q && git status -sb
```
- אם הענף מאחורי `origin/main`, עושים `git pull` קודם.
- אם יש שינויים שלא שייכים לבקשה הנוכחית, אומרים למשתמש לפני שממשיכים. הפריסה בונה מתיקיית העבודה, ולכן גם הם יעלו לאתר.

אם הבקשה עמומה ("תשפר את הפתיח") או שחסר חומר (תמונה, מספר, טקסט מדויק), שואלים שאלה אחת קצרה. לא ממציאים עובדות על העסק: מחירים, דירוגים, המלצות, שנות ניסיון, לקוחות.

## 2. הכללים של הפרויקט

- **עברית ו-RTL.** "הבא" בצד שמאל. שומרים על הצבעים: זהב `#D4AF37` (`text-gold`, `bg-gold`) ורקע `#f5f3ee`.
- **כותבים כמו הקוד שמסביב:** אותן מחלקות Tailwind, אותם דפוסים (מערכים של אובייקטים שמרונדרים ב-`map`), אותה רמת הערות. שינוי קטן ולא שכתוב.
- **סופי שורות:** `Home.jsx`, `AboutSection.jsx`, `TestimonialsSection.jsx` ו-`index.html` הם CRLF. עורכים אותם עם כלי העריכה או עם node, **אף פעם לא עם `sed -i` של Git Bash**, כי הוא מוחק את ה-CR. סקריפט הבדיקה תופס את זה.
- **תמונות:** לא שמים תמונה ישירות ב-`public/images`. המקור נכנס ל-`assets/originals/` ומריצים `node scripts/optimize-images.mjs`, שמייצר WebP מכווץ. מפנים ל-`.webp`. גודל לתמונה חדשה של האתר מגדירים ברשימה `siteImages` בסקריפט.
- **לא מציגים תמונות סטוק או תמונות AI כ"עבודות שלנו".**

## 3. בדיקה

```bash
node .claude/skills/site-update/scripts/check.mjs
```
מריץ build ו-lint ובודק את סופי השורות. אם משהו נכשל, מתקנים לפני שממשיכים.

אחר כך בודקים בעין, בדפדפן מקומי: שרת `preview` מתוך `.claude/launch.json` (localhost:4173), או `npm run build && npm run preview`. גוללים לאזור ששונה ומצלמים בדסקטופ ובנייד (375px). בודקים שאין שגיאות בקונסול ושאין גלילה אופקית (`scrollWidth === clientWidth`).

**מלכודות שכבר נתקלנו בהן:**
- **חלונית דפדפן מוסתרת** מקפיאה אנימציות, וכותרות נראות שקופות. מריצים `document.getAnimations().forEach(a => a.finish())` לפני הצילום.
- **אחרי `scrollIntoView` בנייד** הצילום לפעמים נראה חתוך. בודקים מיקום אמיתי עם `getBoundingClientRect` לפני שמסיקים שיש באג.

## 4. תצוגה מקדימה, ואז אישור

```bash
firebase hosting:channel:deploy preview --expires 7d --non-interactive
node .claude/skills/site-update/scripts/verify-deploy.mjs https://gabayteam-6d556--preview-7z2ku1yn.web.app
```
הערוץ `preview` שומר על אותה כתובת בכל פריסה. אם הכתובת שהפקודה מחזירה שונה, משתמשים בזו שהיא מחזירה. `verify-deploy` מוודא שהכתובת מגישה בדיוק את ה-build המקומי ושכל התמונות נטענות.

מציגים למשתמש:
1. **מה השתנה:** משפט או שניים במילים שלו, לא שמות קבצים. "שעות הפעילות בשישי עכשיו 7:00–13:00."
2. **הקישור לתצוגה המקדימה**, כדי שיפתח גם בטלפון.
3. **צילום אחד או שניים** של האזור שהשתנה, בנייד ובדסקטופ, אם יש כלי לשליחת קבצים (למשל `SendUserFile`).
4. **שאלה אחת:** לפרוס לאתר החי? אם יש כלי של כפתורים (`wrap_up` עם `ask` ו-`actions`), משתמשים בו. כפתור ראשון: "אשר ופרוס", כפתור שני: "צריך שינוי".

**ועוצרים.** לא פורסים לאתר החי באותה תשובה. אם המשתמש מבקש תיקון, חוזרים לסעיף 3 ומעלים שוב לאותה כתובת preview.

## 5. אחרי אישור מפורש בלבד: אתר חי, commit, push

הגדרת "אישור": המשתמש אמר במפורש לפרוס ("כן", "תעלה", "אשר ופרוס"), אחרי שראה את התצוגה המקדימה של השינוי הזה. אישור של עדכון קודם לא חל על עדכון חדש. אם אחרי האישור נעשה עוד שינוי, צריך תצוגה מקדימה ואישור מחדש.

```bash
node .claude/skills/site-update/scripts/check.mjs
firebase deploy --only hosting --non-interactive
node .claude/skills/site-update/scripts/verify-deploy.mjs https://gabayteam.co.il
```
- **תמיד עם `--only hosting`.** `firebase.json` מכיל גם את `dataconnect` (Cloud SQL, עולה כסף) ואת `firestore`.
- **ה-build שנפרס הוא בדיוק ה-build שאושר.** אם אחרי ה-preview השתנה משהו, זה כבר עדכון אחר.

אחר כך commit ו-push של קבצי העדכון בלבד:
- **ההודעה:** בעברית, שורה ראשונה קצרה (כמו בהיסטוריה של הריפו) ושורות פירוט מתחת. שורות הייחוס לפי מה שהסביבה מגדירה.
- **הקבצים:** כולל `.firebase/hosting.*.cache`, שתמיד נכנס עם פריסה בפרויקט הזה.
- **הדחיפה:** `git push origin main`.
- **CLAUDE.md:** אם השינוי הופך משהו שכתוב בו ללא נכון, מעדכנים אותו באותו commit.

מדווחים בקצרה: נפרס ונבדק ב-gabayteam.co.il, ה-commit, ומה עוד פתוח (אם יש).

### גלריית פרויקטים
- **שלב 1:** תמונות המקור (גם ישר מהטלפון) נכנסות ל-`assets/originals/projects/`. נותנים להן שמות באנגלית בלי רווחים, למשל `kitchen-modiin-1.jpg`.
- **שלב 2:** מריצים `node scripts/optimize-images.mjs`, שמייצר `public/images/projects/<שם>.webp` (עד 1600px, מיושר לפי EXIF).
- **שלב 3:** מוסיפים אובייקט ל-`src/data/projects.js`: `id`, `title`, `category`, `description`, `images` עם נתיבי ה-`.webp`. הקטגוריות משמשות לסינון, אז חוזרים על אותם שמות: שיפוצים, מטבחים, אמבטיות, אלומיניום וכו'.
- הגלריה מוסתרת כל עוד הרשימה ריקה. ההוספה הראשונה מציגה אותה.

## 6. מה לא עובר בסקיל הזה

**המלצות.** המקור הוא Firestore, והן מתעדכנות דרך בוט הטלגרם `@Gabayweb3085bot`. בודקים מה המצב:
```bash
curl -s "https://firestore.googleapis.com/v1/projects/gabayteam-6d556/databases/(default)/documents/testimonials?pageSize=1"
```
- **מחזיר `{}`:** האוסף ריק, והאתר מציג את `src/data/testimonials.js`. שינוי שם עובר בתהליך הרגיל.
- **יש מסמכים:** אומרים למשתמש לעדכן דרך הבוט. שינוי בקובץ ישפיע רק על הגיבוי.

**קוד הבוט (`bot/`).** תהליך אחר, בלי preview:
1. מריצים `cd bot && npm test` ומציגים למשתמש מה השתנה.
2. אחרי אישור: commit ו-push, ואז בשרת:
   `ssh berber@2.29.53.208 'cd ~/GabayTeam && git pull -q && cd bot && PATH=~/.local/node/bin:$PATH npm ci --omit=dev && systemctl --user restart gabay-content-bot'`
3. בודקים בלוג: `journalctl --user -u gabay-content-bot`.

בשרת, `gabay-bot.service` הוא הצ'אט של האתר. לא נוגעים בו.

**חוקי Firestore** (`firestore.rules`): אחרי אישור, `firebase deploy --only firestore:rules`. לוקח כמה דקות עד שהם נכנסים לתוקף בכל השרתים, ולכן בודקים עם curl כמה פעמים ברצף לפני שמכריזים שזה עובד.
